# herdr-treehouse

Herdr plugin + CLI engine for a worktree-as-tab workflow. Mental model: **a Herdr workspace is a repo, a tab is a worktree**. See README.md for install and usage.

Longer design reasoning lives in `docs/` (worktree-lifecycle, config, herdr-quirks). Code comments are reserved for gotchas the code cannot show; when a change needs prose beyond that, extend the matching docs/ file instead of commenting.

## Architecture

Three layers, strictly separated:

1. **Engine** (`src/`, entrypoint `bin/treehouse`): all mechanics. Plain Bun/TypeScript CLI, no runtime deps. The plugin manifest, Claude skills, lazygit commands, and keybindings are all just call sites for this one binary.
2. **Manifest** (`herdr-plugin.toml`): declares how Herdr reaches the engine (actions, popup pane, link handlers, `worktree.created` hook). Actions cannot take free arguments; context arrives via env (`HERDR_PLUGIN_CONTEXT_JSON`, `HERDR_PLUGIN_CLICKED_URL`). Every manifest entry is a plain `bin/treehouse <command>`; there are no shell shims doing work of their own.
3. **Personal wiring** (NOT in this repo): `$(herdr plugin config-dir treehouse)` = `~/.config/herdr/plugins/config/treehouse/`, holding `config.toml` and `bootstraps/*.sh`. This repo only ships `config.example.toml`. Keep the committed code generic (no employer-specific repo names, ticket prefixes, or Atlassian sites); that separation is deliberate so the repo stays shareable.

## Key decisions (don't undo casually)

- **Worktree = tab, not workspace.** Herdr's native `herdr worktree open` opens worktrees as workspaces; we intentionally bypass it and use `tab create --cwd`.
- **`autostart = false` is the norm.** Dev commands are pre-filled with `pane send-text` (no Enter). Work is parallel across tabs but verification is serial; two tabs must never race for the same docker containers/ports.
- **`down` never forces.** Refuses on uncommitted changes and on panes with confirmed running processes (double snapshot 750ms apart, because prompt tooling spawns short-lived processes that false-positive a single check). Never kills processes, never `git worktree remove --force`, leaves the branch (PR merge cleans it up).
- **Panes config**: `[[repos.X.panes]]` entries each split the PREVIOUS pane; the first splits the main/agent pane. `[{split="right"}, {split="down"}]` gives agent | halved right column.
- **`setup` vs `bootstrap` are two tiers, keep both.** `setup` is a list of plain shell commands run inside a freshly created worktree — covers most repos (`npm ci`, `cp {root}/.env .env`) without a script. `bootstrap` replaces worktree creation entirely and is for script-grade logic (monorepos). Don't merge them.
- **Git owns where an existing worktree is; `worktree_dir` only says where a new one goes.** `placement.ts` asks git where the branch is checked out before anything derives a path; `up` asks that module once, before building the plan, and passes the answer as the plan's explicit `worktree`. Deriving the path instead meant a worktree made by another tool (or named after a different ticket) was invisible: provisioning tried to create a second worktree for a branch git already had checked out, and git refused after the bootstrap had run. A branch checked out in the main checkout is refused, not opened as a tab. `provision.ts` was the last place asking the other way (#62): `existsSync` made a leftover directory read as "worktree already exists", so setup was skipped and a tab opened on something that is not a checkout of the branch, and placement made that easier to reach since a path git does not know is what it hands over as free. Provisioning asks git itself rather than reading the placement off the plan, because the hook path has no placement to read.
- **A worktree is unique per branch, not per ticket** (#32). `{id}` is the ticket when the branch has one, so two branches of one ticket derive the same `worktree_dir` path, and the second one used to land in the first one's worktree without a word: nothing is checked out there under its name, the directory exists, so provisioning said "worktree already exists" and opened a tab with an agent standing on the other branch. `placement.ts` now asks `worktreePlacements()` for the paths the convention allows (the `{id}` path first, the full-slug path second) and takes the first that no other worktree occupies, which leaves one branch per ticket on exactly the path it has always had. The chosen placement carries its `id` into the plan, so the path, `{id}` in setup and pane commands, and the tab label all name the same worktree (two tabs labelled `🌳 abc-123` would defeat the point, and a `{id}` docker project name would collide the way the paths did). A `worktree_dir` with no room to disambiguate (no `{id}`, e.g. `../{repo}-{ticket}`) yields one placement and is refused, not silently reused.
- **Reopening is a tab problem, not a provisioning problem** (#28). `up` on an existing worktree opens a tab on it and runs nothing; that already covers "I closed the tab and came back". What it cannot see is a worktree that exists but was never provisioned (made by hand, by another tool, or before the repo had a config), so `--setup` is an explicit opt-in rather than a guess from the state of the directory. A third config list for the reopen moment was designed and rejected: the drift it claimed to repair (a moved lockfile) bites after you rebase, which is not when `up` runs, and the case that is real is "setup never ran here", which wants `setup` and not a second list.
- **A repo's config has two legal homes.** A `[repos.X]` block centrally, or `<repo>/.treehouse.toml` (same fields, no wrapper, no `root`), layered `[defaults]` → `[repos.X]` → local. The local file works standalone, so a repo needs no central entry at all. Which home fits is a judgment call about the repo's ownership, which is why `onboard` only exposes `--local` and leaves the choice to the caller.
- **Worktrees are siblings of the main checkout.** `worktree_dir` defaults to `../{repo}-{id}`, and relative paths resolve against the main checkout rather than cwd. Deliberately NOT Claude Code's own `<repo>/.claude/worktrees/` layout: nesting N long-lived worktrees inside the checkout puts copies of the tree in the path of watchers, test globs, build contexts and workspace globs, and needs a per-repo `.gitignore` entry the engine can't guarantee. Sibling also means `cd ../{repo}-{id}` is the whole navigation story.
- **Permission posture belongs at a launch site, never in a skill.** The agent command resolves `--agent` > `.treehouse.toml` > `[repos.X]` > `[defaults]` > bare `claude`. `[defaults].agent` is the home for flags wanted in every worktree tab; bare `claude` instead inherits `permissions.defaultMode` from the user's own Claude Code settings. Both are legitimate, and which one carries the posture is the user's call, not the engine's, so don't "consolidate" a configured `[defaults].agent` into settings.json. A per-repo `agent` is for repos that genuinely deserve different treatment, not for restating a global preference. Skills must never inject permission flags: that hides the decision in markdown and makes the skill path behave differently from `treehouse up`.
- **Standing context is config text, delivered as a system prompt** (#35). A repo's `context` is what the agent in a worktree tab cannot see for itself (branch, ticket, which targets got dependencies, that the dev pane is pre-filled), and it lives in the treehouse config because the plugin is a layer above the work code, which is the only option for repos the user does not own. `--prompt` is not that channel: it is a task carrying judgment from whoever asked. Delivery is `--append-system-prompt`, not a first user message, which reads as the task and ages out on compaction. That makes it agent-specific, so the config owns the *text* and the `agent` line owns *how it arrives*, through `{context_file}` (legal only there, the way `{targets...}` is legal only in bootstrap argv). The rendered text goes to a throwaway file outside any repo, one per repo and `{id}`: multi-line text inside a `pane run` command string sits badly with bracketed paste, and a `treehouse context` subcommand could not re-derive `--target`, which is an `up` invocation fact. Half-configured is refused rather than silent (`context` nothing reads, `{context_file}` with nothing to put in it), and the engine writes no instructions of its own: with `{branch}`, `{ticket}`, `{worktree}` and `{targets}` the user writes them, and the engine gains no judgment.
- **A model is an invocation fact; the flag that carries it is config** (#46). The defect `--model` fixes is that `--agent` can only *replace*: changing one word means restating the rest, and a repo with `context` set makes that mandatory rather than tedious (a short `--agent` is refused for lacking `{context_file}`). The copy then restates `--dangerously-skip-permissions` wherever it was generated, which is the one thing the permission-posture decision above keeps in a single place. So the engine learns no flags: `model_arg` (`'--model {model}'`) holds the spelling in the config beside the agent command, `{model_arg}` says where it goes, and `--model` supplies the value. Deliberately no `model` config key: a default would be maintenance every release for a value that should follow whatever an ordinary session picks, and an alias the agent resolves itself survives them. Empty is a *complete* answer, which is where this differs from `context`: with no `--model` the slot renders to nothing and the command reads as it always did, so an unused `model_arg` passes. A slot with no key behind it passes for a different reason worth keeping straight (it is the mirror of `{context_file}` with no `context`, which is refused): the mistake surfaces the moment it matters, since the next `--model` there is refused for having nowhere to go, while an unread `context` never surfaces at all. Only a model that would be silently *dropped* is refused. Rejecting a general `--agent-args` was about the *caller*, not the engine: an opaque appended string teaches the engine nothing either, but it puts the agent's flag spelling back in the skill layer and lets a caller append permission flags. `docs/worktree-lifecycle.md` has both arguments.
- **Where the config lives is Herdr's answer, so the config asks for it instead of repeating it** (#49). A bootstrap's `argv[0]` needs an absolute path, so every config spelled out `herdr plugin config-dir treehouse`'s layout, a path we do not own and that a pre-1.0 Herdr may move. `{config_dir}` is an ordinary placeholder carrying that value, `configDir` on `PlanInput`; `up` and `bootstrap` are the only plan builders and both resolve the dir into a local before handing it to both the config resolution and the plan, so the two cannot disagree about it. Anchoring relative bootstrap paths at the config dir was the alternative and was rejected: it changes what an existing relative path means (today it resolves against the main checkout, which is the *repo*, by accident of `cwd`), and it reads two ways for a repo configured by a local `.treehouse.toml`, where the repo is the natural anchor. That is also why `{config_dir}` only ever means one thing: a repo-local config's script belongs in the repo, and today's anchor already finds it. Legal wherever ordinary placeholders are, since a setup command may copy a template from there; refused in `worktree_dir` alone, because a worktree does not belong in the config dir, so a `worktree_dir` naming it is broken config. That refusal is a choice and not a constraint (the value is a plain string, so `worktreePlacements()` could carry it too), and the price of allowing it would be threading the dir through `inventory.ts` and `report.ts` for a path nobody should write. The write side follows the same rule: `renderProposedBlock` proposes `{config_dir}/bootstraps/<repo>.sh` centrally and `{root}/scripts/worktree-up.sh` for a repo-local file, since each home has its own anchor.
- **Related Claude skills** wrap this engine: `herdr-worktree`, `herdr-worktree-teardown`, `herdr-repo-onboard`. They are judgment layers and live outside this repo; keep mechanics out of them, in the engine.

## Module seams

The commands are thin; everything reusable sits behind a module with one job. Keep it that way when adding features. The folders are those jobs grouped by what they know about, and they layer in one direction — `config/` knows nothing else, `worktree/` and `herdr/` know only `config/`, `deps.ts` wires them, `commands/` uses all of it, `main.ts` dispatches:

```
src/main.ts        entrypoint: argv in, one command out (process wiring behind import.meta.main)
src/cli.ts         flag declaration, parsing, help rendering
src/deps.ts        the dependency seam (invoker, env, log/warn, ask)
src/worktreeCount.ts   recount from git, report the sidebar token, warn on failure
src/commands/      one file per treehouse subcommand + registry.ts, the one registry
src/worktree/      the git/worktree domain: branch naming, plan, placement, provision, git
src/herdr/         everything that knows Herdr: invoker, tab choreography, env payloads
src/config/        config shape, validation, resolution, defaults; diagnostics severity
src/testing/       fake Herdr, temp repos, resolved configs, expectRejection
src/manifest.test.ts   the manifest <-> code contract, which belongs to no single layer
```

Tests stay next to what they test (`up.ts` / `up.test.ts`); the two that pin code against `herdr-plugin.toml` (`manifest.test.ts`, `worktree/branch.test.ts`) read it from the repo root.

### `src/worktree/` — the git domain

- `branch.ts` — the naming convention in one place: branch to ticket, branch to slug, and clicked URL to branch. Pure functions returning values; `up` merges the derived branch and the focus decision itself. The URL patterns are declared twice by necessity (Herdr gates on the manifest's `[[link_handlers]]` before the engine runs), so `branch.test.ts` reads `herdr-plugin.toml` and pins one sample URL per handler to both declarations. Keep them anchored and host-scoped like the manifest.
- `plan.ts` — everything derived about one worktree (path, base ref, slug/ticket/id, placeholder expansion) from a single `buildWorktreePlan()` call. Pure: no fs, no git, no Herdr. An unknown `{placeholder}` is an error, not a pass-through. `bootstrapTakesTargets()`, `agentCommandTakesContext()` and `agentCommandTakesModel()` answer whether asking for targets is wanted, and whether a context file and a model slot are; the `{targets...}`, `{context_file}` and `{model_arg}` placeholders themselves are private. `{targets}` (the comma-separated prose form) expands like any other placeholder but is refused in bootstrap argv, where it can only be a mistyped `{targets...}`; `{context_file}` and `{model_arg}` are refused everywhere except `expandAgent()`, and `{model}` everywhere except `expandModelArg()`, each being the only expansion that can supply a value for it. `{config_dir}` is ordinary everywhere except `worktree_dir`, which is resolved from `placeholderValues()` (shared with `worktreePlacements()`) and deliberately never sees it. `worktreePlacements()` is the pure half of #32: the ordered `{id, worktree}` spots the convention allows one branch, which `placement.ts` picks from and hands back through `worktree` + `id`. `conventionalId()` is the same naming rule with no path in it, for the callers that must name a branch whose placement cannot be derived.
- `placement.ts` — the impure half of the same question, and the one module that answers it: it asks git whether a worktree is already there, and answers which path a branch's worktree gets, which short name that path goes by, and the two refusals (a branch checked out in the main checkout, and every legal path taken by another branch). `unplaceable()` names the answer for a worktree standing where no placement can be derived, so `up` and the inventory cannot drift on it. It may ask git, the way `provision.ts` does, which is exactly what `plan.ts` may not do. `up` asks once between resolving the config and building the plan, `inventory.ts` asks which placement a worktree it already has a path for stands on; neither holds placement logic of its own. Tested against a temp repo with no fake Herdr, since git is the only thing that knows which spots are taken.
- `inventory.ts` — one record per linked worktree of a configured repo, assembled from the git module and the repo's config (naming via `branch.ts`, managed flag and `id` via the `placement.ts` answer for the worktree it stands on, so a disambiguated path reads as conventional and under the name `up` gave it). Assembles only; `ls` renders, and nothing acts on the records (a `prune` command was specced and dropped, see below). Herdr facts enter through `attachTabFacts()` as plain data, so the module keeps the layering rule (worktree/ never imports herdr/) while `ls` merges pane snapshots into the records.
- `provision.ts` — "make this worktree exist and be usable", shared by `up` and the `worktree.created` hook. `worktreeState: 'just-created'` is how the hook says Herdr already made the checkout but it is still fresh, so `setup` must run, and `setupExisting` is how `up --setup` says the opposite: the worktree is old but setup belongs there anyway. Setup expands its whole command list before running any of it, so a typo'd placeholder stops the run before the first command has changed the worktree. Whether a worktree is already there is asked of git, not of `existsSync` (#62), and what is in the way is what `git worktree add` refuses (a path with files, a file, a dangling symlink), not merely a path that exists; a worktree git lists whose directory is gone gets its own refusal naming `prune`/`remove`. Two exemptions, both tested: `just-created`, and a `bootstrap`, which owns creation and may be handed an existing directory.
- `agentContext.ts` — the agent command assembled: the repo's `context` rendered and put where the command can read it, plus a `--model` dropped into the repo's `model_arg` slot. Its own module because `plan.ts` is pure (no fs) and `provision.ts` is about making the worktree exist, which this file is not part of. Owns the refusals on both features (`context` with no `{context_file}`, `{context_file}` with no `context`, `--model` with no `model_arg` or no `{model_arg}`) because each pair is only visible together, and `up` calls it before provisioning so they fail ahead of `npm ci`. Returns the command *and* the file it wrote, so `up` can name it in its summary and a test can assert against it instead of scanning the temp dir for the name.
- `git.ts` — the only module that knows git, the way `tabs.ts` is the only one that knows Herdr: argv, ref shapes, and the flags that must NOT be there. Callers ask questions (`inspectCheckout`: root, main root, linked, dirty in one call; `findWorktreeForBranch`: which worktree holds a branch, main checkout included so the caller can refuse it; `findWorktreeAtPath`: which branch occupies a path, the question `existsSync` answers wrong, sharing the module's `samePath` so git's spelling of a path and a derived one compare equal) and name intents (`addWorktree` with the branch-exists and base-refresh policy inside, `removeWorktree` without `--force`, pinned by `git.test.ts` against real repos).

### `src/herdr/` — the Herdr seam

- `tabs.ts` — the only module that knows Herdr: subcommand names, response decoding, and the quirks (split chain, autostart vs pre-fill, wait-idle + paste + explicit Enter, always an explicit `--pane`, the double busy snapshot). Also the home of plugin identity: `PLUGIN_ID` (pinned to the manifest by `manifest.test.ts`) and `pluginConfigDir()`. `up`/`down` must contain no herdr subcommand strings. `listPanes()` is the read-only pane snapshot (no busy-check waiting) that `ls` feeds into the inventory; `reportWorkspaceMetadata()` owns the metadata-token call shape (source id, wall-clock seq, max TTL as the staleness backstop).
- `invoker.ts` + `testing/fakeHerdr.ts` — the invoker is a dependency (`EngineDeps.invoke`), with a spawning adapter for production and a recording fake for tests. Responses stay `unknown` so decoding happens once, in `tabs.ts`. `unpackHerdrResponse` is the spawning half's own seam: argv and spawning on one side, a pure function of the finished spawn on the other (envelope, bare body, non-zero exit, a spawn that never started), so the shape `tabs.ts` decodes against is pinned by the adapter that meets Herdr and not only by the fake. `invoker.test.ts` drives `tabs.ts` over it; drift in Herdr itself still needs a live session (`docs/herdr-quirks.md`).
- `context.ts` — the only reader of the payloads Herdr hands the engine through the environment: `HERDR_PLUGIN_CONTEXT_JSON` (invocation context) and `HERDR_PLUGIN_EVENT_JSON` (`worktree.created`). Both decode tolerantly, keeping the raw payload for the plugin log and treating the fields as absent, because neither a malformed context nor a malformed event may take the invocation down. Also the home of `TREEHOUSE_TARGET_PATH` (one env convention for "which repo or worktree"). `commands/action.ts` (`treehouse action up|down`) resolves it and opens the popup. `invocationTargetPath()` answers what the invocation named and leaves `undefined` to the caller (`action` has its own answer for nothing named); `requireInvocationTarget()` is the answer with cwd in it, and owns the refusals for the invocations where cwd is the plugin's own repo (#58, `docs/herdr-quirks.md` also records the module that was deliberately not built above it).

### `src/config/` — the config shape

- `config.ts` — one shape declaration (keys *and* value shapes, per level) validated in one pass; takes a resolved config dir, never a Herdr invoker. The resolvers (`resolveRepoConfig`, `configuredRepoName`, `resolveAllRepoConfigs`) report their own diagnostics through `diagnostics.ts` before returning, so a call site cannot obtain a usable config while an unreported error sits in the data (unknown keys warn, wrong value shapes stop the run). `resolveAllRepoConfigs` is the multi-repo view (`ls`, `report`): same layering per repo, but a repo whose own block is broken is skipped with a warning instead of stopping the listing. The defaults live here *and are applied here*, by both resolvers, so `RepoConfig` promises `base`, `worktree_dir` and `panes` (pane `split`/`ratio`/`autostart` included) and a consumer cannot forget a fallback; keys with no default stay optional, which is what keeps `bootstrap?.length` and `context === undefined` readable. The validator entry points are private for the same reason the diagnostics are reported inside: the resolvers are the way in, so `config.test.ts` drives validation through them rather than behind them. Also the home of `renderProposedBlock`, the write side of the shape: onboard hands it a value and the round-trip through resolution is pinned in `config.test.ts`.
- `diagnostics.ts` — the `Diagnostic` type and the severity decision (warnings print, errors throw). The type lives here, with the module that acts on it, so the folder has no import cycle.

### `src/` — the shell

- `deps.ts` — the environment is a dependency, not a global reach: `EngineDeps.env` defaults to `process.env` in `resolveDeps` and is threaded to every env fact the engine reads (invocation context, clicked url, target path, caller pane/tab, event payload, plugin config dir, `HERDR_ENV`). `src` reads the global in exactly two places, the entrypoint and that default. Output works the same way: everything a command prints goes through the resolved `log`/`warn`, so no module keeps a console default of its own. Input too: `ask` is the seam for every interactive question (up's popup, down's confirm, the entrypoint's hold-open), with a readline adapter as the production default, so tests script answers and record what was asked and no command touches stdin directly.
- `cli.ts` — each command declares its flags once with help text attached; parsing and `--help` both derive from the declaration, so help cannot drift.
- `worktreeCount.ts` — the one "recount and re-report the sidebar token" step, shared by `up` and `down`. It sits at the shell level rather than in `worktree/` or `herdr/` because it needs both the git count and the Herdr report, and those two folders may not import each other. Warning instead of throwing is the module's own rule (a sidebar decoration must never fail a command); *when* each command reports is the call site's, and those comments stay there.

### `src/commands/` — the verbs

One file per `treehouse` subcommand, each named after the command it implements (`up`, `down`, `ls`, `onboard`, `action`, `bootstrap`, `report`), and nothing else in the folder except:

- `registry.ts` — the one registry: each entry is a command's declaration plus its handler, so dispatch, help and parsing read the same list and adding a command is one entry, in one place. `main.ts` looks up by name and runs; it has no per-command switch, takes argv and deps as parameters, and keeps its process wiring behind `import.meta.main` so it can be imported in tests.

A command file is allowed to be thin and boring: it parses its flags, asks the modules below for facts and intents, and prints. Logic that outlives one command belongs in `worktree/`, `herdr/` or `config/`, not here.

## Development

```bash
bun install
bun run typecheck        # tsc --noEmit, no build step (bun runs .ts directly)
bun test                 # unit + command-level tests, no Herdr session needed
herdr plugin link .      # re-run after editing herdr-plugin.toml
herdr plugin log list --plugin treehouse   # event/action stderr logs
```

Herdr CLI responses are JSON; `src/herdr/invoker.ts` wraps invocation and returns the parsed `result`. Never construct pane/tab IDs; always read them from responses.

Tests run with no Herdr session and no `HERDR_ENV`: pass `{ invoke }` from `createFakeHerdr()` plus the `env` the test wants (`{ HERDR_ENV: '1', ... }`), and the whole command runs against scripted responses while recording the Herdr calls it made. No test saves or restores `process.env`. Tests that need real git mechanics use `createTempRepo()` (throwaway repo, worktrees as siblings inside it). Live verification is still required for anything that touches Herdr's own behaviour; the fake proves the sequence, not that Herdr accepts it.

## Status / open ends

- `worktree.created` hook: **observed live** (herdr 0.7.5). Payload is `{event, data: {type, workspace, worktree}}` with `data.worktree.path` and `data.worktree.branch`, matching `herdr api schema`. It provisions through the same module as `up`, so a repo with only `setup` is covered too. Decoded in `context.ts` and covered end to end by `commands/bootstrap.test.ts`; the raw payload is still logged on every run, so a shape change shows up before the fields quietly read as absent.
- The action entrypoints (`treehouse action up|down`) log the raw `HERDR_PLUGIN_CONTEXT_JSON` to stderr, so `herdr plugin log list --plugin treehouse` is where to look when a popup targets the wrong repo. Confirmed live field names: `workspace_cwd`, `focused_pane_cwd`, `focused_pane_id`, `clicked_url`, `invocation_source`.
- **Prompt submission (herdr 0.7.5), three live-verified quirks, all handled in `tabs.ts`:** `herdr wait agent-status` no longer exists; it is `agent wait <pane> --until idle` plus `agent prompt <pane> <text>`, and `agent prompt` owns submission, so the old `pane run` + explicit `send-keys enter` workaround for bracketed paste is gone. `pane run <pane> <agent>` still starts the agent, but Herdr registers it only once detection sees it, so `agent wait` answers `agent_not_found` for the first second or two. And an agent can report `idle` while its TUI is still starting, which silently swallows the prompt: submit with `--wait --until working` so Herdr confirms delivery, and resubmit when it fails. Do NOT branch on the error code there - a swallowed prompt comes back as `agent_prompt_stalled` or `timeout` depending on how Herdr's 5000ms change-detection window races the `--timeout` (keep `--timeout` well above 5000ms). Ask the agent instead: `agent get <pane>` reports a `state_change_seq` that advances whenever the agent moves, so an unchanged sequence means nothing was picked up and resubmitting is safe.
- **Context delivery (`{context_file}`), live-verified (herdr 0.7.5):** `pane run <pane> <command>` hands the command to the pane's own shell, which evaluates it, so `claude --append-system-prompt "$(cat <file>)"` reads the file and multi-line content arrives as one argument. That is the whole premise of writing the context to a file, so it was checked in a scratch pane before the feature was merged rather than assumed. The `worktree.created` hook is unaffected and stays that way: it provisions only, never resolves an agent command, so there is no command line to hang `{context_file}` on. One asymmetry follows - a half-configured repo (`context` with no `{context_file}`) provisions fine through the hook and only fails on `up`.
- `down` treats a registered agent in `idle`/`done` as not busy (tearing it down is the point); `working`/`blocked` agents and non-agent processes still refuse.
- `up` currently requires `HERDR_ENV=1`. Planned (pending the owner deciding Herdr is a keeper): degrade gracefully outside Herdr by running bootstrap only and skipping tab/panes/agent.
- **Sidebar token (`$worktrees`, issue #26 MVP)**: `treehouse report` pushes the per-repo worktree count as workspace metadata. Freshness comes from four sides: `up`/`down` report in-process after changing the count (Herdr's worktree events see only its native flow, not our git-side changes), the manifest's `worktree.created/removed` hooks cover the native flow, `workspace.focused` covers plain git (#45: nothing else sees a raw `git worktree remove`, and focus is when the sidebar is read), and `[[startup]]` re-reports after a server restart (tokens are not persisted). The focus hook re-reports *every* configured repo because every workspace row is on screen at once; reasoning in `docs/worktree-lifecycle.md`. Per-worktree tokens (`$ticket`, `$dirty`) and PR enrichment were deliberately cut from the MVP: dirty/ahead-behind change on git activity, which no hookable event sees, so their sidebar freshness story is unsolved (noted in #26).
- Overlap with the `vk-branch` skill's worktree mode is known and intentionally left until that decision. Details in `~/.claude/CLAUDE.md` under "Herdr + treehouse".
